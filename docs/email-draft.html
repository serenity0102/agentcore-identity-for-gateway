Hi [Name],

I tested whether an Amazon Bedrock AgentCore Runtime agent that queries and updates Amazon Redshift respects the access control that Redshift gets from AWS IAM Identity Center (IdC). In short, it does, as long as the agent propagates the caller's identity rather than using a service credential. Below are the architecture, setup, test steps, results, and a few gotchas worth knowing before we recommend this pattern to customers.

TL;DR
  • Every agent query runs in Redshift as the real IdC user (AWSIDC:wei@…), so Redshift grants, column-level grants and RLS defined for IdC groups apply unchanged. 16/16 allow/deny cases matched expectations.
  • The agent's IAM role has no Redshift permissions. Without a user's token it cannot reach the data at all. Prompt injection could not escalate privileges, because Redshift still denied the statements.
  • The network is locked down: Redshift accepts 5439 only from the runtime's NAT EIP and the operator IPs. I verified this with Redshift's connection log and a revoke/restore test.
  • AgentCore Identity pattern: this validates On-Behalf-Of (OBO), with the token exchange done through IAM Identity Center trusted identity propagation. It is not 2LO, 3LO or SigV4-to-data. Details in section 1.1.
  • 2LO and 3LO were tested too (Part 2, separate runtime; OBO unchanged and re-verified at 16/16). With 2LO every user, including one with no grants, sees all rows and PII, because Redshift only sees a service user. With 3LO, Token Vault isolation and session binding work, but I found a shared-browser risk; an agent-side identity check fixes it. 18/18 cases passed.
  • Two gotchas: external JWTs are single-use at IdC, and an Allow-only IdC app ActorPolicy does not stop same-account admins. Fixes are below.

1. Test architecture

The IdC instance lives in ap-east-1, where AgentCore is not available. The runtime therefore runs in ap-southeast-1 (the nearest region with AgentCore) and reaches Redshift in ap-east-1 through a NAT Gateway with a fixed Elastic IP. AgentCore Gateway was not needed because the agent calls Redshift directly with the user's token, which keeps the identity chain to one hop.

Identity flow: user's browser → local Web chat GUI (http://localhost:8080) → Cognito managed login (auth code + PKCE) → Cognito ID token (JWT, kept server-side by the GUI) → AgentCore Identity inbound JWT authorizer → agent → sso-oauth:CreateTokenWithIAM (IdC customer-managed app, Trusted Token Issuer maps the Cognito email to the IdC user) → IdC access token → Redshift (token_type=ACCESS_TOKEN) → session user AWSIDC:<email> with roles AWSIDC:<group>.

1.1 Which AgentCore Identity pattern does this test validate?

Mapped against the four patterns in the AgentCore Identity Deep Dive deck (SigV4, 2LO, 3LO, OBO), this test validates On-Behalf-Of (OBO), the token-exchange pattern:

PatternUsed?How it shows up in this test
OBO (token exchange)Yes, coreThe agent already holds the user's token (Cognito JWT) and exchanges it, with no extra user consent, for a downstream token scoped to Redshift: an IdC access token with scope redshift:connect, via CreateTokenWithIAM using the jwt-bearer grant (RFC 7523). The downstream service (Redshift) then enforces its own per-user policies (grants, column grants, RLS). Each session exchanges once; no Token Vault, no refresh token. These are exactly the OBO traits on the deck's OBO slide: "downstream enforces per-user access, requires JWT inbound".
Inbound JWT (Agent Authorizer)YesAgentCore Identity's customJWTAuthorizer validates the Cognito JWT before the agent runs (401 on missing or forged tokens). OBO requires JWT inbound; SigV4 inbound would lose the user.
SigV4 (execution role)Supporting onlyThe runtime role only authenticates the exchange call (CreateTokenWithIAM is an IAM-signed API, restricted by the IdC app ActorPolicy) and calls Bedrock. It has no Redshift permission, so data access never runs as the agent itself.
2LO (client credentials)Separate test (§5)The OBO agent never authenticates to Redshift as itself. Section 5 shows what happens when it does (a service account).
3LO (auth code + consent)Separate test (§5)The OBO flow has no browser consent and no stored resource token. Section 5 exercises 3LO with the Token Vault and session binding.

Difference from the deck's OBO flow:

  • Who does the exchange. In the deck, AgentCore Identity's Credential Provider (using the agent access token, WAT) or a Gateway target with grantType: TOKEN_EXCHANGE performs it against the downstream IdP. Here the downstream IdP is IAM Identity Center, whose exchange (CreateTokenWithIAM) is an IAM-authenticated AWS API rather than a standard OAuth token endpoint. So the agent code performs it with its execution role, and the WAT, Credential Provider and Token Vault are not used. Whether the Credential Provider or Gateway can drive this natively is worth confirming with the service team.
  • What the downstream token carries. The deck's OBO token carries both user and agent identity. Here Redshift sees the user (AWSIDC:<email>). The agent's identity is the IdC application that requested the token, and CloudTrail records the runtime role's exchange call.
  • Why forwarding fails. Our first attempt simply forwarded the user's JWT to Redshift (EXT_JWT) and broke on the second connection, because IdC treats a JWT as single-use. This is why OBO's audience-scoped downstream token, rather than a forwarded JWT, is the right pattern.

2.1 Trusted Token Issuer: "IdC trusts JWTs issued by Cognito"

IAM Identity Center does not sign users in here; Cognito does. The Trusted Token Issuer (TTI) tells IdC that a JWT signed by this Cognito user pool is acceptable proof of who the user is, and how to find the matching IdC user. It is configured once on the IdC instance (Settings → Authentication → Trusted token issuers):

TTI setting (rsidc-cognito)Value and meaning
Type / Issuer URLOIDC_JWT · https://cognito-idp.ap-southeast-1.amazonaws.com/ap-southeast-1_kSVpAo5yl. The token's iss must equal this
JWKS retrievalOPEN_ID_DISCOVERY: IdC fetches Cognito's signing keys via the discovery document and verifies the signature
Claim → identity store attributeemail → emails.value: the JWT's email must match exactly one IdC user
Applications that trust itrsidc-redshift (AuthorizedTokenIssuerList) and rsidc-data-agent (jwt-bearer grant). Each accepts only audience kff7mg63m7d94n6f2euip41na (the OBO Cognito client)

At exchange time IdC checks, in order:

  1. The issuer matches and the signature is valid.
  2. aud is authorized for that application.
  3. The token is not expired and has not been redeemed before (single use).
  4. email matches exactly one IdC user. Example: Cognito wei → wei@techfinance.example.com → IdC user wei → Redshift AWSIDC:wei@techfinance.example.com.
  5. The user's groups are assigned to the application.
Because email is the mapping key, Cognito users must be admin-created with verified emails; self sign-up is disabled.

3. Test steps

Everything is scripted and idempotent (infra/01…08). The full commands and the real output of each step are in the attached RUNBOOK.md.

  1. Create the runtime VPC with private subnets and a NAT Gateway with a fixed EIP (ap-southeast-1).
  2. Create the Cognito user pool (admin-only) and four users mirroring IdC emails.
  3. Create the IdC Trusted Token Issuer and the Redshift IdC application (AWSIDC), then assign groups.
  4. Create the Redshift cluster, with the SG restricted to the runtime EIP and the operator IPs.
  5. Seed the tables, create the AWSIDC:<group> roles, grants, column grant and RLS policies (admin via the Data API).
  6. Create the runtime execution role (no Redshift permissions).
  7. Create the IdC customer-managed app for the agent's token exchange, with an explicit-Deny ActorPolicy.
  8. Deploy the agent to AgentCore Runtime (VPC mode, JWT authorizer, header forwarding).
  9. Run the access-control matrix through the runtime: each persona signs in once and uses one runtime session.
  10. Run the negative, security and network tests.

5. Part 2: 2LO and 3LO test cases

To compare the other AgentCore Identity outbound patterns, I added a separate runtime (rsidc_oauth_agent), so the OBO runtime and its tests were not touched. After Part 2 the OBO matrix still passes 16/16 and the OBO runtime is still at version 3.

2LO architecture: the agent authenticates as itself (client credentials) → AgentCore Gateway → Redshift service user.

3LO architecture: the user consents once; AgentCore Identity keeps the user's token in the Token Vault (session binding by the app).

Who authenticates what (2LO / 3LO). Both the runtime and the Gateway have inbound JWT authorizers that trust Cognito:

  • Runtime: the user's ID token, audience = OBO client.
  • Gateway: the M2M access token, allowedClients = 2LO client.
  • AgentCore Identity is the runtime's outbound broker. It fetches tokens from Cognito (M2M, or the user's token from the Token Vault). The Gateway doesn't trust AgentCore Identity; it validates the Cognito-issued token against Cognito's JWKS.
  • Gateway outbound: its IAM role invokes the Lambda.
  • 3LO: there is no Gateway; Cognito userInfo validates the user's token itself.

6. Findings and recommendations

  1. Redshift enforces the access control, not the agent. IdC groups surface as AWSIDC:<group> roles, so existing grants and RLS apply to agent traffic exactly as they do to direct users.
  2. External JWTs are single-use at IdC (jti replay protection). Passing the JWT straight to Redshift (EXT_JWT) fails on the second connection. Recommended pattern: the agent exchanges it once via CreateTokenWithIAM and reuses the IdC access token (about 1 hour) inside the session. A new session needs a fresh or refreshed user token.
  3. An Allow-only IdC app ActorPolicy is not a boundary against same-account admins. Add an explicit Deny for all principals except the agent role, and ideally an SCP.
  4. Authenticated ≠ authorized. App assignment controls who can sign in; Redshift grants control what they can see.
  5. Column grants silently trim SELECT *. zhang's SELECT * on sales.orders returned 4 columns with no error; customer_email was simply omitted. Only naming the column explicitly is denied. Tell agent and report builders, because "no error" does not mean "all columns".
  6. Metadata is visible by default. Users can list tables they cannot read. Enable Redshift metadata security if table names are sensitive.
  7. Network: keep Redshift reachable only from known egress IPs. Corporate networks can egress different ports via different IPs, so detect the IP actually used for 5439.
  8. 2LO bypasses per-user data controls by design. Even a user with no grants saw PII through the service account. Use 2LO only for data every caller may see, and authorize at the tool level (Gateway allowedClients and scopes).
  9. 3LO shared-browser risk. Session binding checks the app user, not the account the browser signed in with at the IdP. Add an agent-side check that the vault token's subject matches the caller (verified here), and offer a forced re-consent to recover.
  10. prompt=login via customParameters shows the login form but led to no stored token. Confirm with the AgentCore Identity team before relying on it. It also needs Cognito managed login v2.
  11. The Data API is an IAM path, not a network path. The security group does not govern it. Scope GetClusterCredentials to a single DB user and consider VPC-endpoint or IP conditions.

7. Cost and cleanup

About USD 0.72/hour while running (Redshift ra3.large ≈ 0.65, NAT ≈ 0.065; AgentCore Runtime, Gateway, Lambda, Bedrock and Cognito are negligible at test volume). infra/99-teardown.sh removes everything, including the Redshift cluster with no final snapshot. It does not touch the existing IdC instance, users or groups.
